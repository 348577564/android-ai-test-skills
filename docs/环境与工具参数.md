# 环境搭建与工具全参数

> SKILL.md 的附录。**只在首次搭建环境、或需要查某个参数时读**，日常执行用不到。

## 环境搭建（一次性）

### 一键安装（推荐）

```powershell
pwsh -File scripts/setup.ps1
```

依次做：检查 adb → 检查设备 → 建 venv 装依赖 → 初始化 uiautomator2 → 自检。

| 参数 | 用途 |
|---|---|
| `-SkipDeviceCheck` | 没插设备也先装依赖 |
| `-Recreate` | 重建已存在的 venv（venv 被占用时会给出提示） |
| `-SkipDeps` | 只建 venv，不装依赖 |
| `-Python <路径>` | 显式指定解释器 |

### 手动安装

```powershell
python -m venv .venv
.venv\Scripts\pip install -r requirements.txt
adb devices -l                              # 设备在线且已授权
.venv\Scripts\python -m uiautomator2 init   # 设备端初始化（每台设备一次）
```

### ⚠️ Python 版本：3.10 ~ 3.12（**有上限**）

| 边界 | 原因 |
|---|---|
| **≥3.10** | `pillow 12` 起要求 `>=3.10`（3.9 装不上新版 pillow） |
| **≤3.12** | `rapidocr-onnxruntime` 的元数据写死 `requires_python="<3.13"` |

**3.13 上会直接失败**：

```
ERROR: Could not find a version that satisfies the requirement rapidocr-onnxruntime>=1.3.0
(from versions: ..., 1.2.3)
```

即 3.13 上 rapidocr 最高只能装到 **1.2.3**，装不了我们要求的 1.3.0+。

> 想支持 3.13 的话，得把 `requirements.txt` 里 rapidocr 放宽到 `>=1.2.3`（代价是用旧版 OCR）。
> 当前选择是**保新版、限解释器**。

`setup.ps1` 会自动挑出合格解释器；机器上若只有 3.13，它会**列出被拒的解释器与原因**，
不必自己猜。也可用 `py -0p` 看本机装了哪些。

## 命令前缀

以下命令省略前缀 `.venv\Scripts\python tools\`。

- 多设备加 `--serial <serial>`；改证据目录加 `--dir`
- `--name` 可省略，缺省自动派生 `<会话id>/step<N>`
- **`--serial/--dir/--name/--full/--no-filter/--settle/--perm-action` 写在子命令前或后都可以**
  （如 `act.py --settle 1500 tap ...` 与 `act.py tap ... --settle 1500` 等价）

## session.py —— 会话生命周期

```powershell
python session.py start --title "日历新建课程表" --input "用户口述的用例原文..."
python session.py finding --status PASS --event-id <证据事件ID> --expect "出现创建成功toast" --actual "OCR读到'创建成功'"
python session.py finish --status PASS --summary "4 步全过，无异常弹窗"
```

| 子命令 | 说明 |
|---|---|
| `start --title --input [--case <id>] [--device] [--package] [--related] [--diag]` | 开会话 |
| `finding --status --expect --actual [--event-id <ID>] [--note] [--id]` | 记断言；PASS/FAIL/WARN 必须绑定证据，多个 ID 重复传参 |
| `finish --status --summary [--package] [--id]` | 收尾写结论 |
| `pause --reason [--ask]` / `resume --id --note` | 遇阻暂停 / 恢复 |
| `perm-intent --action grant\|deny [--perm] [--clear\|--show]` | 声明权限响应意图（**不声明默认 grant**；测拒绝路径时才用） |
| `case add/list/show/update/save` | 用例库维护 |
| `paths [--id]` | 采集路径边 → 生成**待确认草稿** `storage/pending_paths.md`（`finish` 时已自动做） |
| `paths-apply [--only 1,3]` | 把草稿写入路径图（人确认后执行；`--only` 只挑几条） |
| `list` / `current` / `abandon` | 查看 / 解绑 |

要点：

- **中文长文本用 `@文件` 传参**（`--input @case.txt`，UTF-8）——命令行直传中文
  在部分终端管道里会被 GBK 双重解码；expect/actual/summary 同理。
- finding 的 expect/actual 必须是**具体判据**（dump 字段值 / OCR 文本），不能只写"正常"。
- 从观察/动作/OCR 返回的 `event_ids` 显式选取支持断言的事件；跨会话、无证据或证据文件不存在的引用被拒绝。BLOCKED/ERROR 可不带验证证据，但 actual 必须说明原因。
- `finish` 校验通过后才事务提交结论和用例统计；拒绝或写入失败退出码 1，保留当前会话。PASS 只允许 PASS findings，WARN 允许 PASS/WARN；FAIL 必须存在 FAIL finding。BLOCKED/ERROR 必须有 summary 原因。
- 历史记录只补结构，不自动伪造证据关联。历史已完成会话保持原状；未完成会话若存在无证据断言，不能以 PASS/FAIL/WARN 提交，需核实后以 ERROR/BLOCKED 说明原因收尾，重新执行时正确关联证据。
- 证据绑定不代表模型判断正确，也不能证明原始用例预期全部覆盖，须逐项审计。正式完成的会话不能再次 finish。
- **正式用例进用例库**：首次跑通后 `case save --session <N>` 提升；
  复跑 `start --case <id>` 自动带出标题与文本。
- **验证/调试跑动加 `--diag`**：工具自检、探针验证等非正式测试的会话，
  不进「测试记录」库、不计入仪表盘成功率。
- **用例结束自动采集路径边**：`finish` 时把「落脚点 → 锚点 → 去向」累积到
  `knowledge/paths/<包名>.md`（**不看会话结论**，FAIL/BLOCKED 里走过的路径也有效）。
  一般不用手动跑；需要补采时 `paths --id <N>`。

## run.py / audit.py —— 独立调用对账与耗时基础设施

基准通过独立启动器执行；工具参数原样传给对应工具：

```powershell
.venv\Scripts\python tools\run.py session start --title "基准" --input "<用例>" --package com.app
.venv\Scripts\python tools\run.py --session-id <会话ID> observe --full
.venv\Scripts\python tools\run.py --session-id <会话ID> act tap --x 540 --y 1200
.venv\Scripts\python tools\run.py session finding --event-id <ID> --status PASS --expect "<预期>" --actual "<实际>"
.venv\Scripts\python tools\run.py session finish --status PASS --summary "<结论>" --no-paths
.venv\Scripts\python tools\audit.py --session-id <会话ID>
```

- `run.py` 支持 act/observe/read/session/state/logcat/vision。正式基准的设备观察、动作和 OCR 调用必须绑定已有会话。
- `--session-id` 写在工具名前；工具自己的参数放在工具名后。不指定时读取当前会话；多设备仍须给工具传 `--serial`，该接口不宣称支持并行会话调度。
- 启动前持久化 `storage/calls/<session_id>/<call_id>.json`（未绑定时在 `unbound`），结束后补充退出状态、子进程墙钟时间与工具返回。旧平铺清单首次读取时一次性分目录，后续 guard 只扫描本会话。清单失败时不开始动作；结束记录失败仍保留工具输出，并在 stderr 单独报告 `audit_failed`，不会重放已执行动作。
- 工具成功返回的 `event_ids` 与同 `call_id` 的数据库事件对账。成功却没有主事件、会话不符或 ID 不一致，启动器以非零退出并报告审计错误。
- `audit.py` 再次读取清单与数据库，报告未结束调用、失败调用、漏事件及无独立清单的事件。`ok` 与退出码只表示记录完整性：0 为完整，1 为不完整；完整记录的拒绝/失败尝试列入 `failed_attempts`，不污染完整性，也不代表用例通过。没有调用清单不判完整。
- 返回 `execution_state` 区分 `not_executed`、`executed`、`may_have_executed` 与 `unknown`。终态拒绝和连接失败未执行，不生成记录损失标记；动作异常、返回缺失不能默认未执行，仍须保守对账并禁止自动重放。state 全部子命令和 logcat crash/clear 也要求主事件；logcat setup 不要求事件。
- 清单之外仍需宿主 transcript 判断有没有调用根本未到达启动器；对账不证明执行内容或测试结论正确。
- 不自动删除历史 recording_errors 标记；旧版本误标与真实缺证据需依据原调用记录区分，不能为放行会话直接清空标记。
- 记录不完整标记保存到 `storage/recording_errors/<session_id>/`，后续设备调用被拦截，禁止重放；该会话只允许以 ERROR/BLOCKED 并说明原因收尾。标记写失败也会显式报错，不保证故障磁盘仍可写。

计时解释：

| 字段 | 范围 |
|---|---|
| `wall_ms`（调用清单） | 子工具进程启动至退出，包括子进程启动、导入和连接；不包含整个宿主调用或启动器自身全部开销 |
| `session_wall_ms`（audit） | 会话 started_at 至 finished_at，含模型、调度及人工等待；未结束返回 null，不等于整个宿主任务耗时 |
| `duration_ms`（事件） | 核心操作区间：连接完成后至采集、签名与崩溃检查完成；OCR 包含导入/初始化、图像获取与结果转换。均不包含初始连接、事件写入、节点返回构建与序列化；不是完整 CLI 墙钟时间 |
| `timing.process_observed_ms` | 从 runtime 模块载入开始，到生成该快照；更早导入与进程启动不在此区间 |
| `timing.stages_ms` | 实测阶段：设备导入/连接、动作、等待、权限、采集、崩溃检测及取证、节点处理、记录、序列化、OCR 导入/初始化/推理/图像信息/结果转换；未出现的阶段不是零 |
| `response_bytes` | 启动器收到的 stdout UTF-8 字节数，包含换行；不等于模型 token 数 |
| `tool_interval_ms`（audit） | 相邻所选调用的前次结束到本次开始，含宿主/人工/启动器开销，不等于模型推理；负数提示重叠或时钟变化 |

证据元信息和数据库事件保存的是当时的计时快照。默认模型可见返回不带 timing；启动器通过独立 `storage/timing/<call_id>.json` 读取较晚快照写入清单。诊断时可设置 `ANDROID_TEST_VERBOSE_TIMING=1` 展开返回。不能把不同快照或 `wall_ms` 与阶段耗时相加；crash_evidence 是 crash_detection 的子区间，不能重复累计。OCR 库内部预处理/后处理无法独立拆出（包含在推理阶段），宿主推理仍为未知。暂停/人工等待按宿主记录另行区分。

回归隔离可指定绝对存储目录（不要指向正在使用的目录）：

```powershell
$env:ANDROID_TEST_STORAGE = "D:\TestArtifacts\android-baseline"
```

数据库、当前会话、默认证据、崩溃指纹、调用清单、计时、路径草稿、cleanup 清理范围及 vision 配置使用该目录。应用知识卡仍是共享资产，`paths-apply` 会修改它，不用于隔离回归。Web 测试台的文件服务与视觉配置页仍按默认仓库路径组织，隔离产物通过 CLI 审计；隔离 vision 需单独提供该目录下的配置。

终态后 state 改状态操作与 logcat clear/setup 被拦截；logcat crash、已有图片的 read/vision 仍可用于取证复核。finish 已提交但当前指针损坏或清理失败时返回成功并带 `self_check` 警告，保持指针供人工处理，不重复提交。

## act.py —— 动作

```powershell
python act.py tap --x 540 --y 1200 --via rid=com.app:id/btn_ok --why "点击保存" --name c1/s2
python act.py longclick --x 540 --y 1200 --name ...
python act.py input --x 540 --y 1200 --text "你好" --via text="确定" --why "填写标题" --name ...
python act.py input --x 540 --y 1200 --text "追加" --no-click --append --name ...  # 已聚焦不重复点击；追加不覆盖
python act.py swipe --from 540,2000 --to 540,800 --dur 300 --name ...
python act.py back --why "关闭二级页" --name ...      # home / key --code N 同理
```

| 参数 | 说明 |
|---|---|
| `--x/--y` | 坐标，从**本次** nodes 取（禁止复用旧坐标） |
| `--via` | 定位依据（本次坐标从哪个元素推出来），路径图采集靠它 |
| `--why` | 这一步的理由（时间轴展示）；back/home/key 也支持 |
| `--settle <ms>` | 稳定窗口，默认 600（写在前后都行） |
| `--perm-action grant\|deny` | 声明权限意图（**测拒绝路径时才需要**；不声明默认同意） |
| `--perm <类型>` | 配合 `--perm-action`，如 `media_images`/`camera` |
| `--watch <specs>` | App 自定义瞬态弹窗，阶段用 `;;` 分隔、阶段内候选用 `\|` |
| `--watch-timeout <ms>` | watch 总窗口，默认 8000 |
| `--full` | nodes 给全量语义节点（默认 nav：只给可点/可滑动节点） |
| `--no-filter` | 不过滤非前台包的节点 |

执行动作 → 稳定窗口 → **自动再做一次 observe**，一个调用回传"动作 + 动作后画面"。

## 执行录屏（recorder.py）—— 与「轨迹回放」不是一回事

- **执行录屏** = `session start` 起、`finish` 止，`adb shell screenrecord` 直出 mp4 →
  `storage/evidence/<sid>/rec.mp4`，路径写回 `sessions.recording`，WebUI 用 `<video>` 播。
- **轨迹回放** = `webui._replay` 把 events 里的截图按时间轴串帧播放，时长 = 会话真实时长，
  与录屏无关。所以"回放好几分钟、录屏只有几秒"通常是录屏本身没录上。

### 方案（2026-10-22 重构：单文件连续录制）

**做法**：整场会话只录一个文件，全程无分段、无拼接。

```
启动：setsid sh -c 'screenrecord --time-limit 0 /sdcard/.rec_<sid>.mp4' &
停止：kill -INT $(pidof screenrecord)   →  screenrec 正常收尾写 moov → pull 回本地
```

三条关键事实（实测，本机 ZUI / Android 14 基线）：

| 事实 | 影响 |
|---|---|
| `--time-limit 0` = **不限时长**（默认才是 180s 上限） | 长会话不需要分段续录 |
| `kill -INT` 是 screenrecord 的**正常停止方式**（文档："until Ctrl-C is hit"） | 停止即收尾，`moov` 完整，**不用等段边界**；实测 18s 录制→17.96s 可播 |
| `kill -TERM` / `KILL` 会留下只有 mdat、没有 moov 的废文件 | 停止**只能**用 SIGINT，禁止 TERM/KILL |
| `setsid` 让录制脱离 adb 会话（PPID=1） | 发起 start 的工具进程退出后录制继续 |

**为什么放弃分段**（2026-10-21 的 30s 分段方案）：每段重启时 screenrecord 约有
0.5s 起播延迟，这段画面永久丢失；时间戳虽被 ffmpeg 拼接掩盖，但画面内容会"跳"。
实测同一 90s 会话：分段方案有 9 处 >120ms 空洞（最大 0.96s），单文件方案 **0 处**。

### 产物与自检

- 正常：`evidence/<sid>/rec.mp4`（单文件，原生分辨率 3840×2560，约 0.7Mbps / 25fps）
- 收尾异常（SIGINT 丢失等）：写 `evidence/<sid>/rec_incomplete.json` 并置 `recording=NULL`
  —— 绝不把不可播文件塞给 WebUI
- 完整性自检：实际时长 vs 录制窗口偏差 >20% 时写 `rec_incomplete.json`

### 调参（环境变量）

- `DSH_REC_SEGMENT` / `DSH_REC_MAX_SEGMENTS`：**仅在回退的分段模式下生效**
  （无 serial 时才会走该分支），默认 30s / 240 段。
